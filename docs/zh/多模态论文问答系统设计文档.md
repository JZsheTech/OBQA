# 📘 PaperQA 系统设计文档（精简版）

## 一、系统模块设计

Evidence#no 表示 evidence number。

| 模块                     | 设计说明                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Evidence 生成策略**      | 在 Answer 生成阶段，LLM 自动输出带有 `[Evidence#no]` 锚点的文本。每个锚点对应一个已索引的 Element（包含 `bbox`），前端可据此实现高亮定位。                                   |
| **索引元素结构**             | MinerU 解析得到的 `content_list` 中的每个对象即为一个 **Element**，作为最小索引单元。Element 可为文本、图片、表格、公式等，实现多模态统一索引与检索。                              |
| **Answer–Evidence 绑定** | Answer 中通过 Markdown 锚点 `[Evidence#no]` 内嵌引用；前端点击锚点即可跳转并高亮对应内容。                                                                |
| **高亮系统**               | 基于 MinerU 提供的坐标 (`bbox`) 信息进行前端高亮渲染，实现原文级可视化溯源。                                                                               |
| **系统结构**               | 系统由四个核心 Agent 协作组成：**Control Agent**、**Retrieval Agent**、**Memory Agent**、**Answer Agent**。OceanBase 作为统一的索引与向量存储层，确保扩展性与一致性。 |

## 二、详细设计：Pipeline 流程

### 🧩 P1. 文档上传与索引

1. **解析阶段**

   * 使用 MinerU 对上传的 PDF 进行解析，得到 `content_list`（包含文本与图片）和文本形式的全文`md_text`。

2. **文档入库**
	- 将文档全文`md_text`存入 `Documents` 表，关联到所属的 `Collection` ，并获得collection_id、文档id。

3. **标题层级修复**
   * 调用 `preprocess_header()` 扫描并修复章节层级结构（依据标题模式如 `1`, `1.1`, `2.1.2` 等），为每个 Element 增加：
     * `header_name`：最近的上一级标题名称
     * `level_nav`：完整的层级导航路径, 比如 1. introduction > 1.1 GNN > 1.1.1 message passing

4. **章节聚合与摘要生成**

   * 以层次结构聚合各个章节内容：从当前标题到下一个同级标题之间的所有文本按顺序拼接。
   * 利用简易摘要模型为每个章节生成摘要（summary），并存入对应 header 节点。

5. **Element 结构统一化**
   为统一检索格式，所有 Element 均需具备 `text_content` 与 `image_content` 两部分字段：

   * **pure_text**：`text_content = header_name + level_nav + text_content`
   * **header**：`text_content = header_name + level_nav + section_summary`
   * **image**：`text_content = header_name + level_nav + image_caption`
   * **table**：`text_content = header_name + level_nav + table_caption`
   * **equation**：`text_content = header_name + level_nav + equation_text (LaTeX)`
   * **image/table/equation** 的 `image_content` 为原始 base64 图片数据。

6. **向量化与存储**

   * 统一调用qwen系列多模态 embedding 模型进行嵌入：
     * 文本类（Text、Table、Equation）：使用 `text_content` 生成嵌入向量(Table、Equation嵌入时不用图片模态)
     * 图片类（Image）：使用 `image_content` 生成嵌入向量
   * 将嵌入结果及元信息（collection_id、doc_id 等）写入 OceanBase 的 `Elements` 表中。

---

### 💬 P2. 问答流程

7. **提问与改写**

   * 用户选择一个目标 `Collection` 并提出问题。
   * 调用阿里 LLM 对 `question` 进行 query 重写（query rewriting），得到更适合检索的语句。

8. **向量检索与 Evidence 生成**

   * 使用改写后的 query 在 `Elements` 表中进行向量检索。
   * 检索结果按类型（header、text、table、equation、image）分类，送给AnswerAgent判断哪些是有用的，把有用的留下来，结合chat_id中之前已有的Evidence，去重后继续向后编号，比如`[Evidence#3]`, `[Evidence#4]` 等。
   * 更新 `Turn2Evidence` 表，保存该turn使用到的evidence_no、element_id

9. **Answer 生成与绑定**
   * 构造 Prompt：
     * 文本模态：将多个 `text_content` 以分隔符拼接，并注明对应的 Evidence no；
     * 图片模态：将 base64 图片依序存入 `images` 列表，并在 Prompt 中明确说明每个idx处的图片与 Evidence no. 的对应关系。
   * 调用阿里多模态 VLM 模型（text + image 输入），生成带 `[Evidence#no]` 锚点的 Answer。

10. **前端交互**

   * 前端解析 Answer 中的 `[Evidence#no]` 锚点，依据对应 element、 的doc_id、 `bbox` 与 `page_no` 定位并高亮原文内容，实现 Answer–Evidence 可视化联动。
