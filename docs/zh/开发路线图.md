## 串行阶段划分（6 个里程碑）

> 每个阶段均给出**完成判定（DoD）**与**主任务清单（按实现顺序）**。按此顺序逐项完成即可。

### M0. 开发环境与空仓库骨架（目标：能启动空 API）

**DoD：** 本机/服务器上，`uvicorn` 能启动 FastAPI；前端能以最简页面发起 GET 健康检查。
**主任务：**

6. 建立 2 个 Conda 环境：`quest`（FastAPI、DSPy）与 `jzMinerUVllm`（MinerU 本地服务）；启动 OceanBase Docker（最小单节点）。
7. 组织仓库目录（建议）：`backend/`、`frontend/`、`dependency/`（直接指向现有样例）。
8. 后端创建最小路由组：`GET /healthz -> {ok:true}`。
9. 前端用最薄的 fetch 封装连通健康检查（无需状态管理框架）。

---

### M1. 数据库初始化与仓储层（目标：表可用、CRUD 可测）

**DoD：** OceanBase 中六张表建成，后端可通过仓储函数完成基本 CRUD，`GET /api/collections` 能返回空列表。
**主任务：**

10. 依据统一数据模型编写 DDL：

   * 表：`collections / documents / elements / chats / turns / turn2evidence`；
   * 关键外键：`documents.collection_id`、`elements.doc_id`、`turns.chat_id`、`turn2evidence.chat_id/turn_id/element_id` 均采用 `ON DELETE CASCADE`；
   * 主键：`turn2evidence` 使用 `(chat_id, evidence_no)`（evidence 编号在 chat 内连续递增）。
   * 性能索引延后到端到端流程稳定后再评估与添加。
11. 实现**无 ORM**的表网关（仓储层）：`collections_repo.py / documents_repo.py / elements_repo.py / chats_repo.py / turns_repo.py / t2e_repo.py`。
12. 用 `dependency/oceanBaseDemo` 的连接示例打通连接与事务处理。

---

### M2. 文档上传→MinerU 解析→入库（目标：首个 PDF 成功落表为元素）

**DoD：** 前端上传一个 PDF，后端同步串行：调用 MinerU→获得 `content_list + md_text`→标准化→写入 `documents/elements`，前端能在“文档列表”看到该 PDF。
**主任务：**

13. 后端 `POST /api/collections/{id}/documents`（multipart）：控制服务接收文件、保存元信息、**阻塞式**调用 MinerU 接口，拿到 `content_list / md_text`。
14. 执行“标题层级修复 + 统一元素化”：为每个元素写入 `header_name / level_nav / page_no / bbox / text_caption` 等字段；Header 节点生成简要 section 摘要文本；遵循“**元素是最小索引单元**”的统一结构。
15. 以**统一文本视图**存入：

   * 纯文本：`header_name + level_nav + text_content`；
   * header：`header_name + level_nav + section_summary`；
   * 图/表：使用 caption 形成 `text_content`，图像 base64 存 `image_base64`。
16. 采用 `dependency/minerUparseDemo/parse_pdf_minerU.py` 作为对接样例起点。

> 备注：与“前端轮询状态”不同，本 Demo 采用**同步入库**以保证单人串行的可控性；此做法与“服务同步、可预测副作用”的蓝图一致。

---

### M3. 向量化与检索（目标：能检向量返回候选元素）

**DoD：** 通过后端脚本或 API 触发对刚入库元素的向量化，完成 `elements.vec_embedding` 写入；`/api/retrieval/test` 能依据查询返回若干候选元素（含类型与元数据）。
**主任务：**

17. 仅文本模态元素（text、header）：仅对 `text_content` 生成向量；同时包含文本与图像模态的元素（image、table、equation）：可按策略联合使用 `text_content` 与 `image_base64` 进行多模态嵌入，或仅使用 `text_content`（caption）进行文本嵌入。采用本地 vLLM 部署的 Jina Embeddings v4（模型名：`jina_embedding_v4`）。先参考 `dependency/multiModalEmbedding` 的 vLLM `/v1/embeddings` 样例，再封装到 `embedding_service.py`。注意：回答阶段 DSPy 仅消费文本上下文，图像内容若需要参与需先转为文字摘要（见 M4）。
18. 在仓储层增加**简单的向量近邻查找**（可先用余弦相似度 + TopK，后续再优化），检索时附带 `doc_id / page_no / bbox / elem_type`。
19. 预留“去重与类型分桶”接口（但先不复杂化）。

补充要求：

- 新增环境变量 `EMBEDDING_ENDPOINT / EMBEDDING_MODEL / EMBEDDING_TIMEOUT_S / EMBEDDING_MAX_RETRIES / EMBEDDING_API_KEY / EMBEDDING_API_KEY_HEADER`，并将 `VECTOR_DIM` 默认值改为 2048 以匹配 `jinaembeddingv4`。
- 后端新增 `services/embedding/embedding_service.py`、`services/retrieval/retriever.py`，仓储层提供 `ElementsRepository.update_embeddings/topk_by_collection/search_fulltext`。
- API `GET /api/retrieval/test` 供联调验证，返回 `{code,data}` envelope。
- 手工验证脚本 `tests/manual/test_m3_embedding_and_retrieval.py`：扫描 `vec_embedding IS NULL` 的元素批量嵌入，并打印检索结果。

### M4. 问答主干（DSPy 文本编排、证据锚点绑定）（目标：能问出带 `[Evidence#no]` 的答案）

**DoD：** 在某 Collection 下创建 Chat，向后端 `POST /api/chats/{chat_id}/turns` 发送问题，返回：`answer` 文本内含 `[Evidence#1]...[Evidence#n]`，并且 `turn2evidence` 表已写入映射，`GET /api/turns/{turn_id}/evidences` 能取到每个证据的 `doc_id/page_no/bbox/snippet`。
**主任务：**

20. 问句重写：使用 DSPy/LLM 先做轻量重写以利检索（文本模型）。
21. 检索：用重写后的 query 进行向量召回，按类型分组与粗过滤，得到候选证据元素。
22. 记忆：仅拼接最近若干轮（例如 3 轮），超限则生成简要摘要文本参与提示词。
23. 答案生成（文本优先）：
    - 默认：仅拼接文本上下文，image/table/equation 仅以 caption 作为 `text_content` 参与；使用 DSPy 文本回答模块，并**显式要求输出锚点**（`[Evidence#no]`）。
    - 可选图像理解：对候选中的 `image` 元素，基于用户 `question` 与检索 `query` 生成 1 个派生子问题；调用独立的视觉问答集成（OpenAI 兼容）按 `element_id` 读取 `image_base64` 后完成一次图文问答，得到“文字摘要”；把该摘要与 caption 合并为新的 `text_content`，再作为文本上下文供 DSPy 使用。
    - 生成后把 `turn_id, evidence_no -> element_id` 写入桥表，确保锚点可追溯。
24. 实现约束：`dspy.Signature` 内不携带任何图片字段；`dependency/DspyDemo` 仅作为文本编排脚手架。视觉问答通过后端 `services/integrations/vision_vqa.py`（建议）独立封装，函数示意：`vision_vqa_summarize(element_id:int, derived_question:str)->str`。

### M5. 最小前端分阶段（M5a–M5d）

为降低复杂度，将原 M5 拆分为 4 个可单独验收的子阶段，按顺序推进即可。

#### M5a. 页面骨架与路由（目标：前端页面可切换）

**DoD：** 前端具备 4 个最小页面/视图并可在路由间正常切换：集合页、文档页（含“上传”占位 UI）、聊天页（消息列表占位）、PDF 预览页（Viewer 占位）。不接后端、仅静态占位与最薄 `fetch` 封装（不实际发请求）。
**主任务：**

25. 建立基础路由与布局骨架；实现上述 4 个页面的最小组件与导航。
26. 预置统一 `fetch` 包装与环境变量读取（仅返回占位数据，不连后端）。

#### M5b. API 对齐与调试（目标：API 连通、统一 envelope）

**DoD：** 通过前端“API 调试面板/页面”或控制台可以成功调用后端最小接口，并看到统一 envelope 的真实返回；错误码与异常路径可观测（成功：`{"code":"OK","data":...}`；错误：`{"code":"SOME_ERROR","message":"..."}`）。
**主任务：**

27. 对齐并接线以下最小 API：

   * `GET /api/collections`, `POST /api/collections`, `DELETE /api/collections/{id}`；
   * `POST /api/collections/{id}/documents`, `GET /api/documents/{doc_id}/file`；
   * `POST /api/collections/{id}/chats`, `GET /api/chats/{chat_id}`；
   * `POST /api/chats/{chat_id}/turns`, `GET /api/turns/{turn_id}/evidences`；
   * 健康检查保留 `GET /healthz`（无 `/api` 前缀）。
28. 前端实现 API 客户端与最小日志/调试视图（打印请求/响应、状态码、耗时），保持统一响应 envelope，仍不做复杂渲染。

#### M5c. 文本形态 QA 展示（不解析 Evidence 跳转）

**DoD：** 在聊天页可选定 Collection/Chat，发送问题后把返回的 `answer` 文本渲染在列表中；答案文本内若含 `[Evidence#no]`，以普通文本形式展示（不可点击）。
**主任务：**

29. 聊天页完成基础交互：创建 Chat、发送问题（`POST /api/chats/{chat_id}/turns`）、渲染问答历史。
30. 处理加载/失败态与最小的输入校验；不做锚点解析与 PDF 联动。

#### M5d. PDF 高亮渲染与锚点跳转

**DoD：** 答案中的 `[Evidence#no]` 可点击；点击后请求 `GET /api/turns/{turn_id}/evidences`，PDF Viewer 根据返回的 `page_no/bbox` 跳转并高亮；多条证据可依次定位；缺失 `bbox` 时给出降级提示。
**主任务：**

31. 在聊天区实现锚点解析与点击处理；
32. 集成/封装 PDF Viewer，支持指定页跳转与基于 `bbox` 的高亮绘制；
33. 与 `GET /api/documents/{doc_id}/file` 联动，按 `doc_id` 加载源 PDF；
34. 对边界情况（无 `bbox`、页码越界、网络失败）给出明确的 UI 反馈。

## 建议的实现顺序（codex 智能体的任务清单）

28. **M0**：初始化 Conda 环境与空 FastAPI；`GET /healthz`。
29. **M1**：执行 DDL 建表；完成 `collections_repo` 与 `documents_repo`，跑通 `GET /api/collections`。
30. **M2**：接入 MinerU 解析接口，完成 `POST /api/collections/{id}/documents` 同步入库；前端做最小上传表单。
31. **M3**：封装 `embedding_service`，对已入库元素批量向量化；实现 `/api/retrieval/test`。
32. **M4**：串联 DSPy：问句重写→检索→答案生成（含锚点）；写入 `turns` 与 `turn2evidence`。
33. **M5a**：前端页面骨架与路由（不接后端）。
34. **M5b**：API 对齐与调试（统一 envelope）。
35. **M5c**：文本形态 QA 展示（不解析 Evidence 跳转）。
36. **M5d**：PDF 高亮渲染与锚点跳转；做 1 套端到端演示脚本。

## M6 验收脚本（端到端自测）

* **创建集合** → `POST /api/collections {name:"Demo"}` 返回 `id`；**上传 PDF** → 返回 `doc_id`；**向量化** → 触发一次批处理；**新建聊天** → `POST /api/collections/{id}/chats`；**提问** → `POST /api/chats/{chat_id}/turns`，响应文本含 `[Evidence#1]`；**点击锚点** → 前端请求 `GET /api/turns/{turn_id}/evidences`，PDF Viewer 定位并高亮。
  以上步骤分别契合**需求**、**数据模型**、**蓝图流程**、**设计与交互**的核心约束。
