## 串行阶段划分（6 个里程碑）

> 每个阶段均给出**完成判定（DoD）**与**主任务清单（按实现顺序）**。按此顺序逐项完成即可。

### M0. 开发环境与空仓库骨架（目标：能启动空 API）

**DoD：** 本机/服务器上，`uvicorn` 能启动 FastAPI；前端能以最简页面发起 GET 健康检查。
**主任务：**

6. 建立 2 个 Conda 环境：`quest`（FastAPI、DSPy）与 `jzMinerUVllm`（MinerU 本地服务）；启动 OceanBase Docker（最小单节点）。
7. 组织仓库目录（建议）：`backend/`、`frontend/`、`dependency/`（直接指向现有样例）。
8. 后端创建最小路由组：`GET /healthz -> {ok:true}`。
9. 前端用最薄的 fetch 封装连通健康检查（无需状态管理框架）。

### M1. 数据库初始化与仓储层（目标：表可用、CRUD 可测）

**DoD：** OceanBase 中六张表建成，后端可通过仓储函数完成基本 CRUD，`GET /api/collections` 能返回空列表。
**主任务：**

10. 依据统一数据模型编写 DDL：

   * 表：`collections / documents / elements / chats / turns / turn2element`；
   * 关键外键：`documents.collection_id`、`elements.doc_id`、`turns.chat_id`、`turn2element.chat_id/turn_id/element_id` 均采用 `ON DELETE CASCADE`；
   * 主键：`turn2element` 使用 `(chat_id, turn_id, element_id)`（不再持久化 `evidence_no`）。
   * 性能索引延后到端到端流程稳定后再评估与添加。
11. 实现**无 ORM**的表网关（仓储层）：`collections_repo.py / documents_repo.py / elements_repo.py / chats_repo.py / turns_repo.py / turn2element_repo.py`。
12. 用 `dependency/oceanBaseDemo` 的连接示例打通连接与事务处理。

### M2. 文档上传→MinerU 解析→入库（目标：首个 PDF 成功落表为元素）

**DoD：** 前端上传一个 PDF，后端同步串行：调用 MinerU→获得 `content_list + md_text`→标准化→写入 `documents/elements`，前端能在“文档列表”看到该 PDF。
**主任务：**

13. 后端 `POST /api/collections/{id}/documents`（multipart）：控制服务接收文件、保存元信息、**阻塞式**调用 MinerU 接口，拿到 `content_list / md_text`。
14. 执行“标题层级修复 + 统一元素化”：为每个元素写入 `header_name / level_nav / page_no / bbox / text_caption` 等字段；Header 节点生成简要 section 摘要文本；遵循“**元素是最小索引单元**”的统一结构。
15. 以**统一文本视图**存入（遵循 M4 中的元素规范）：

   * 纯文本：以 `[doc_title] [page_no] [level_nav]` 作为前缀，拼接当前段落的 `raw_text_content`，并按 `ELEMENT_CONTEXT_OVERLAP` 在同一 `level_nav` 内追加前后若干元素文本作为上下文，形成最终 `text_content`。
   * header：以同样前缀，主体使用 `section_summary`，必要时追加同一章节内的上下文。
   * 图/表：以同样前缀，主体使用 caption（表格额外拼接 markdown 形式的表格正文），图像像素内容存入 `image_base64`，caption 同时保留在 `text_caption` 字段。
16. 采用 `dependency/minerUparseDemo/parse_pdf_minerU.py` 作为对接样例起点。

> 备注：与“前端轮询状态”不同，本 Demo 采用**同步入库**以保证单人串行的可控性；此做法与“服务同步、可预测副作用”的蓝图一致。

### M3. 向量化与检索（目标：能检向量返回候选元素）

**DoD：** 通过后端脚本或 API 触发对刚入库元素的向量化，完成 `elements.vec_embedding` 写入；`/api/retrieval/test` 能依据查询返回若干候选元素（含类型与元数据）。
**主任务：**

17. 仅文本模态元素（text、header）：仅对 `text_content` 生成向量；同时包含文本与图像模态的元素（image、table、equation）：可按策略联合使用 `text_content` 与 `image_base64` 进行多模态嵌入，或仅使用 `text_content`（caption）进行文本嵌入。采用本地 vLLM 部署的 Jina Embeddings v4（模型名：`jina_embedding_v4`）。先参考 `dependency/multiModalEmbedding` 的 vLLM `/v1/embeddings` 样例，再封装到 `embedding_service.py`。注意：回答阶段 DSPy 仅消费文本上下文，图像内容若需要参与需先转为文字摘要（见 M4）。
18. 在仓储层增加**简单的向量近邻查找**（可先用余弦相似度 + TopK，后续再优化），检索时附带 `doc_id / page_no / bbox / elem_type`。
19. 预留“去重与类型分桶”接口（但先不复杂化）。

补充要求：

- 新增环境变量 `EMBEDDING_ENDPOINT / EMBEDDING_MODEL / EMBEDDING_TIMEOUT_S / EMBEDDING_MAX_RETRIES / EMBEDDING_API_KEY / EMBEDDING_API_KEY_HEADER`，并将 `VECTOR_DIM` 默认值改为 2048 以匹配 `jinaembeddingv4`。
- 后端新增 `services/embedding/embedding_service.py`、`services/retrieval/retriever.py`，仓储层提供 `ElementsRepository.update_embeddings/topk_by_collection/search_fulltext`。
- API `GET /api/retrieval/test` 供联调验证，返回 `{code,data}` envelope。
- 手工验证脚本 `tests/manual/test_m3_embedding_and_retrieval.py`：扫描 `vec_embedding IS NULL` 的元素批量嵌入，并打印检索结果。

### M4. 问答主干（DSPy 文本编排、证据锚点绑定）（目标：前端看到 `[Evidence#no]`，后端持久化存储与 API `answer_text` 均使用 `[Elem#id]`）

而且 `[Evidence#no]` 要能够映射到对应的 `elements`。
**DoD：** 在某 Collection 下创建 Chat，向后端 `POST /api/chats/{chat_id}/turns` 发送问题，返回：`answer_text` 文本内含 `[Elem#id]` 锚点，API 响应同时附带 `evidences` 列表（其中每个元素至少携带 `element_id/evidence_no/doc_id/page_no/elem_type/bbox/level_nav/evidence_title/snippet`）；`turn2element` 表已写入映射（仅存 `element_id` 关联，且只为答案文本中真实出现的 `[Elem#id]` 写记录），前端据此将 `[Elem#id]` 渲染为 `[Evidence#no]` 并能高亮 PDF。
**主任务：**

20. 问句重写：使用 DSPy/LLM 先做轻量重写以利检索（文本模型）。
21. 检索：用重写后的 query 进行向量召回，按类型分组与粗过滤，得到候选证据元素。
22. 记忆：仅拼接最近若干轮（例如 3 轮），超限则生成简要摘要文本参与提示词。
23. 答案生成（文本优先）：
    - 默认：仅拼接文本上下文，image/table/equation 仅以 caption 作为 `text_content` 参与；使用 DSPy 文本回答模块，并**显式要求输出锚点**（`[Elem#<element_id>]`）。
    - 可选图像理解(作为一个可选的功能开关)：对候选中的 `image` 元素，基于用户 `question` 与检索 `query` 生成 1 个派生子问题；调用独立的视觉问答集成（OpenAI 兼容）按 `element_id` 读取 `image_base64` 后完成一次图文问答，得到“文字摘要”；把该摘要与 caption 合并为新的 `text_content`，再作为文本上下文供 DSPy 使用。
    - 生成后把 `(chat_id, turn_id, element_id)` 写入 `turn2element` 桥表（仅覆盖答案文本中真实出现的 `[Elem#id]`）；`evidence_no` 由后端按 chat 历史首次出现顺序动态生成映射（收集数据库中该 chat 所有 turn 的 `answer_text`，按照出现顺序解析出所有 `element_id`，做一个去重映射得到 `evidence_no`），并通过 API 响应中的 `evidences` 列表提供给前端用于展示与高亮。
24. 实现约束：`dspy.Signature` 内不携带任何图片字段；`dependency/DspyDemo` 仅作为文本编排脚手架。视觉问答通过后端 `services/integrations/vision_vqa.py`（建议）独立封装，函数示意：`vision_vqa_summarize(element_id:int, derived_question:str)->str`。

### M5. 前端界面落地与联调（M5a–M5g）

基于 `dependency/frontUI_design`（Figma 导出）与《前端页面组织逻辑设计》《前后端交互逻辑设计》，将前端 6 个页面和联调过程拆解为可独立验收的子阶段。

#### M5a. 设计系统 / 工程底座（目标：统一 AppShell、主题、请求封装）

**DoD：** 全局样式 token（色板、字体、间距）与基础组件（AppBar、TopTabs、Breadcrumb、SearchBar、Button、Modal/Drawer）按设计稿落地；AppShell/路由骨架覆盖所有页面；`fetch` 封装处理 `{"code":"OK"}` envelope 与错误 toast，支持 `VITE_API_BASE`；现有健康检查/上传页迁入新框架。
**主任务：**

25. 从 `dependency/frontUI_design` 提取颜色/文字/间距 token，写入全局 CSS 变量与 `App.css/index.css`，落地顶栏 + 二级标签栏 + 面包屑的基础布局。
26. 建立统一路由与布局容器，抽象可复用输入、Card、List Item、搜索条、空状态、分页等组件（按《前端页面组织逻辑设计》命名层级）。
27. 重写 API 客户端：处理统一 envelope、鉴权/环境变量、全局 loading/error 边界与日志钩子；保留 `/healthz` 快捷检查。

#### M5b. 知识库主页（Collections Home）

**DoD：** 列表真实读取 `/api/collections`，支持 name/description 搜索与 Reset，空态/加载态齐备；新建 Collection 弹窗可提交并刷新列表；点击卡片跳转 Collection 管理页。
**主任务：**

28. 实现搜索下拉（按 name/description）、“Searched result” 标签与 Reset 交互，列表行展示 `name/created_at/description` 截断文本。
29. 接入 `POST /api/collections` 新建弹窗（校验必填、错误提示、提交状态），成功后刷新列表。
30. 统一路由跳转：列表行进入 Collection 页，顶部标签栏保持状态，空列表提供创建引导。

#### M5c. Collection 管理页（文档列表 + 上传 + Collection RAG）

**DoD：** 展示 collection 元信息；文档列表读 `/api/collections/{id}/documents`，支持 title/abstract/md_text 搜索视图；多文件上传调用 `POST /api/collections/{id}/documents`，有成功/失败提示；右侧展示 chat 历史与简单 Collection-RAG 检索结果。
**主任务：**

31. 加载 collection 基础信息（name/description/created_at）与文档列表，区分“全部”与“搜索结果”视图，支持空态。
32. 完成多文件上传入口与进度提示，调用 MinerU 入库接口后刷新列表；搜索下拉切换 title/abstract/md_text 的过滤逻辑。
33. Collection 聊天历史：接入 `GET /api/collections/{id}/chats`（若无聚合则按现有接口拼装），条目跳转到 Collection Chat 页面。
34. 简单 Collection-RAG：输入关键词触发检索（可先复用 `/api/retrieval/test` 搭配 `collection_id`），以列表/弹窗展示截断的 `text_content`，支持复制/查看全文。

#### M5d. Document 管理页（meta + Abstract + Document RAG）

**DoD：** 展示 document 元信息（collection/title/file_name/num_pages/element_count），Abstract 卡片可滚动；Document 聊天历史列表可跳转；Document-RAG 检索可返回截断文本并查看全文；支持打开原始 PDF。
**主任务：**

35. 接入文档详情接口（含 meta & abstract，必要时从列表数据补充），以 Chips 呈现数值类信息；提供返回 Collection 链接。
36. Document-RAG 搜索：带 doc_id 的检索调用（沿用 `/api/retrieval/test` 或专用查询），列表 + 详情弹窗 + 复制能力。
37. Document 聊天历史：使用 `GET /api/documents/{doc_id}/chats` 或按 collection-chat 结果过滤，跳转到 Document Chat；增加“打开原始 PDF”（`GET /api/documents/{doc_id}/file`）入口。

#### M5e. Collection Chat 页面（三栏：Chat + 多文档 PDF + Sidebar）

**DoD：** 依据设计稿完成2栏布局(聊天历史作为一个可以从侧边展开的框，不占用主界面空间)；可创建/切换 collection 级 Chat，发送问题后展示 `answer_text` 并将 `[Elem#id]` 渲染为 `[Evidence#no]`；可在文档下拉中切换 PDF 并按 `page_no/bbox` 高亮证据。
**主任务：**

38. 搭建 Chat 面板（消息气泡、输入框、发送按钮、加载/失败态）+ PDF Viewer + 聊天历史 Sidebar 的布局与状态管理。
39. 打通 Chat 生命周期：`POST /api/collections/{id}/chats` 创建、`GET /api/chats/{chat_id}` 加载历史、`POST /api/chats/{chat_id}/turns` 发送提问并追加到消息流。
40. 证据渲染：解析 `answer_text` 中 `[Elem#id]`，结合响应内 `evidences` 或 `GET /api/turns/{turn_id}/evidences` 生成 `[Evidence#no]` tag，点击后触发 PDF 跳转；缺失 bbox 时降级提示。
41. PDF 联动：文档下拉加载 `GET /api/documents/{doc_id}/file`，绘制 bbox 高亮，处理页码越界/加载失败；提供“打开原始 PDF”。

#### M5f. Document Chat 页面（两栏 + Sidebar）

**DoD：** 固定单文档的聊天工作区可发送问题并渲染证据，高亮固定文档 PDF；Sidebar 展示 document 级 chat 历史并可切换。
**主任务：**

42. 复用 Collection Chat 组件，锁定一个 `doc_id` 的 PDF Viewer 与证据高亮；载入 chat 时校验 doc_id 匹配。
43. 聊天历史与创建：沿用 `POST /api/collections/{collection_id}/chats`（附 doc_id）或现有文档聊天接口创建，`GET /api/chats/{chat_id}` 加载历史并刷新 PDF 高亮。
44. 处理无 bbox/多页证据的提示，保证“打开原始 PDF”与聊天侧边栏状态一致。

#### M5g. Chat 历史页与全局导航收束

**DoD：** “Chat 历史” 顶部标签页可按类型过滤，分别列出 collection chat 与 document chat（按 created_at 排序），条目可深链到对应聊天页；面包屑/顶部标签与其它页面保持一致。
**主任务：**

45. 根据后端可用接口聚合聊天列表（若无汇总接口则通过 `GET /api/collections` + 各自 chat 列表拼装），支持分页/空态。
46. 完成过滤器（全部/collection/document）与跳转逻辑，确保从历史页进入聊天后 PDF 与 evidences 正确加载。

## M6 验收脚本（端到端自测）

* **创建集合** → `POST /api/collections {name:"Demo"}` 返回 `id`；**上传 PDF** → 返回 `doc_id`；**向量化** → 触发一次批处理；**新建聊天** → `POST /api/collections/{id}/chats`；**提问** → `POST /api/chats/{chat_id}/turns`，响应中 `answer_text` 含 `[Elem#id]`，并附带 `evidences` 列表；**点击锚点** → 前端解析 `answer_text` 与 `evidences` 将锚点显示为 `[Evidence#1]` 等，并在用户点击后请求 `GET /api/turns/{turn_id}/evidences`，PDF Viewer 定位并高亮。
* **前端走查** → 依次打开：知识库主页（搜索/新建）、Collection 页（上传/搜索/Collection-RAG）、Document 页（Abstract、Document-RAG、聊天历史、PDF 下载）、Collection Chat（三栏证据高亮）、Document Chat（单文档证据高亮）、Chat 历史页过滤与深链；确保响应 envelope、错误提示、加载/空态均符合设计。
  以上步骤分别契合**需求**、**数据模型**、**蓝图流程**、**设计与交互**的核心约束。
