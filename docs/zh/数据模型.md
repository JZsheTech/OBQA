
# 🧩 数据模型设计说明

> 本系统采用统一的全局数据表结构，不为不同的 `collection` 建立独立的 `documents` 或 `elements` 表。所有文档、元素与会话数据均在同一逻辑空间中维护，以便于跨论文检索与统一索引管理。

---

## 一、基础表（Base Tables）

### **1. collections**

| 字段            | 类型          | 说明            |
| ------------- | ----------- | ------------- |
| `id`          | BIGINT (PK) | 主键，自增 ID      |
| `name`        | VARCHAR     | Collection 名称 |
| `created_at`  | DATETIME    | 创建时间          |
| `description` | VARCHAR     | Collection 描述 |


**约束：**
* `PRIMARY KEY (id)`

---

### **2. documents**

| 字段              | 类型          | 说明            |
| --------------- | ----------- | ------------- |
| `id`            | BIGINT (PK) | 主键，自增 ID      |
| `collection_id` | BIGINT (FK) | 所属 Collection |
| `title`         | VARCHAR     | 论文标题（优先取首个 header 文本，回退为文件名） |
| `md_text`         | TEXT     | 论文转换后的markdown格式的全文        |
| `abstract`     | TEXT     | 论文摘要文本（按 MinerU 解析结果中 `Abstract` 标题后的首个元素提取） |
| `file_name`     | VARCHAR     | 文件名           |
| `file_path`     | VARCHAR     | 文件落盘路径          |
| `file_sha256`   | VARCHAR     | 文件内容的 SHA-256 哈希，用于去重 |
| `file_size_bytes` | BIGINT   | 文件字节大小        |
| `num_pages`     | INT         | 页数            |
| `element_count`     | INT         | 文档包含的元素总数     |
| `meta_info`     | JSON        | 额外的元数据（如解析/上传来源、跨系统同步标识等，默认留空） |
| `created_at`    | DATETIME    | 创建时间          |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (collection_id)` → `collections(id)` ON DELETE CASCADE
  
> `collection_id + file_name + file_sha256` 作为上传去重键，防止同一 PDF 被重复解析入库。
> 摘要提取规则：在 MinerU `content_list` 中找到标题为 “Abstract” 的 header，它后续的第一个非 header 元素即为摘要正文；未命中则留空。

---

### **3. elements**

| 字段              | 类型                                     | 说明                                       |
| --------------- | -------------------------------------- | ---------------------------------------- |
| `id`            | BIGINT (PK)                            | 主键，自增 ID                                 |
| `doc_id`        | BIGINT (FK)                            | 所属文档                                     |
| `order`         | INT                                    | content_list中解析出的阅读顺序，从0开始                    |
| `elem_type`     | ENUM('text','header','image','table','equation') | 元素类型                                     |
| `header_name`  | VARCHAR                                | 章节标题，如1.1.1 message passing(不包括父标题)  
| `header_level`  | INT         | 章节标题层级，只有header类型的元素才有。                              |
| `level_nav`     | VARCHAR                 | 层级导航信息，如 1. Introduction > 1.1 GNN > 1.1.1 Message Passing      |
| `text_content`  | TEXT                                   | 增强后的文本内容：包含 `[doc_title] [page_no] [level_nav]` 前缀以及根据 overlap 规则拼接的上下文，用于向量检索与回答上下文 |
| `raw_text_content`  | TEXT                               | MinerU 原始文本内容（按元素类型聚合），不带前缀与 overlap，仅用于调试与构造上下文，不直接参与向量检索 |
| `text_caption`  | TEXT                                   | 图片或表格caption注解                                |
| `image_base64`  | TEXT                                     | 图片内容（Base64 编码）                          |
| `bbox_json`     | JSON                                   | 元素在 PDF 中的位置信息, 4个int组成的列表（bounding box） |
| `page_no`       | INT                                    | 页码                                       |
| `vec_embedding` | VECTOR                                   | 向量嵌入（用于相似度检索，维度由环境变量 `VECTOR_DIM` 配置） |
| `order_start` | INT                                   | Header 元素对应章节在阅读顺序中的起始索引（基于 `order`） |
| `order_end` | INT                                   | Header 元素对应章节在阅读顺序中的结束索引（基于 `order`） |
|                 |                                        |                                          |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (doc_id)` → `documents(id)` ON DELETE CASCADE

> 向量维度通过环境变量 `VECTOR_DIM` 配置。

---

### **4. chats**

| 字段                | 类型          | 说明                   |
| ----------------- | ----------- | -------------------- |
| `id`              | BIGINT (PK) | 主键，自增 ID             |
| `collection_id`   | BIGINT (FK) | 所属 Collection；`type="collection"` 时必填，其余为空 |
| `document_id`     | BIGINT (FK) | 所属 Document；`type="document"` 时必填 |
| `type`            | VARCHAR     | 对话范围，`collection`（默认）或 `document` |
| `created_at`      | DATETIME    | 会话创建时间               |
| `title`           | VARCHAR     | 对话标题                 |
| `max_turn_order` | BIGINT      | chat 内最新轮次序号，从 1 起递增 |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (collection_id)` → `collections(id)` ON DELETE CASCADE
* `FOREIGN KEY (document_id)` → `documents(id)` ON DELETE CASCADE
* 业务规则：`type="collection"` 时 `document_id` 为空；`type="document"` 时 `collection_id` 为空

---

### **5. turns**

| 字段                 | 类型          | 说明                      |
| ------------------ | ----------- | ----------------------- |
| `id`               | BIGINT (PK) | 主键，自增 ID                |
| `chat_id`          | BIGINT (FK) | 所属会话                    |
| `order`            | INT         | 当前turn在chat中的顺序         |
| `user_question`    | TEXT        | 用户问题                    |
| `llm_answer_text`  | MEDIUMTEXT  | LLM 的回答（内部使用 `[Elem#<element_id>]` 锚点；不直接存储 `[Evidence#no]`，对应其他文档中的 `answer_text` 字段） |
| `llm_thought_text` | MEDIUMTEXT  | LLM 的推理过程（思考链）          |
| `created_at`       | DATETIME    | 创建时间                    |
| `response_tokens`  | INT         | 记录当前轮token消耗            |
| `used_llm_model`   | VARCHAR     | LLM 模型标识（如 llama3:70b 或 qwen2.5vl:72b） |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (chat_id)` → `chats(id)` ON DELETE CASCADE

## 七、桥表（Bridge Table）

用于记录每一轮对话（Turn）中引用到的元素（Element）。
在本版（M4）中，系统仅存储 `turn2element`（不再持久化 `evidence_no`）。
`evidence_no` 为展示层编号，由后端在返回 API 前按元素在该 chat 中的首次出现顺序动态生成，并通过 `evidences` 列表暴露给前端。

---

### **Turn2Element（表）**（实际表名：`turn2element`）

| 字段            | 类型          | 说明                                                     |
| ------------- | ----------- | ------------------------------------------------------ |
| `chat_id`     | BIGINT (FK) | 所属会话 ID，对应 `chats(id)`                                 |
| `turn_id`     | BIGINT (FK) | 所属轮次 ID，对应 `turns(id)`                                 |
| `turn_order`  | INT         | 当前 turn 在 chat 内的顺序（冗余字段，用于快速恢复上下文）                    |
| `element_id`  | BIGINT (FK) | 关联的文档元素 ID，对应 `elements(id)`                           |
| `created_at`  | DATETIME    | 记录创建时间                                                 |

---

**约束：**

* `PRIMARY KEY (chat_id, turn_id, element_id)`
  → 保证同一 chat 的同一 turn 内同一元素只记录一次。
* `FOREIGN KEY (chat_id)` → `chats(id)` ON DELETE CASCADE
* `FOREIGN KEY (turn_id)` → `turns(id)` ON DELETE CASCADE
* `FOREIGN KEY (element_id)` → `elements(id)` ON DELETE CASCADE

> 性能相关索引（例如 `(turn_id, element_id)` 等）将于端到端流程稳定后再评估与添加，避免过早承诺。


---

## 三、结构要点总结

* 所有表均为 **全局共享结构**，不同 `collection` 的数据通过collection_id外键区分。
* `documents.title` 优先取解析后元素列表中首个 `elem_type == "header"` 的标题文本，若解析失败或仅有占位 `root`，则回退为 PDF 文件名。
* `level_nav` 不包含论文主标题，仅表示从文内首个标题开始的章节路径，使用 `" > "` 连接各级标题，并保留 MinerU 解析后的大小写。
* `elements` 表是核心索引层，支持多模态内容检索（文本 + 图像 + 表格）。回答阶段（DSPy）基于 `text_content` 进行向量检索与文本上下文拼接；`raw_text_content` 仅用于调试与构造 overlap 上下文，不直接参与检索。若需要利用图像语义，则由后端集成读取 `image_base64` 调用视觉问答接口，将结果转为文字再回注为对应元素的 `text_content` 使用。
* `turn2element`：动态绑定 Turn ↔ Element，实现证据引用关系的记录与追踪，仅为回答文本中真实出现的 `[Elem#id]` 写入记录。
* `evidence_no` 不再入库；由后端在 API 输出前按“元素在该 chat 中首次出现顺序”动态生成（从 1 开始），并通过 `evidences` 列表提供给前端。
