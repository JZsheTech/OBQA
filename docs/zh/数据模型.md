
# 🧩 数据模型设计说明

> 本系统采用统一的全局数据表结构，不为不同的 `collection` 建立独立的 `documents` 或 `elements` 表。所有文档、元素与会话数据均在同一逻辑空间中维护，以便于跨论文检索与统一索引管理。

---

## 一、基础表（Base Tables）

### **1. collections**

| 字段            | 类型          | 说明            |
| ------------- | ----------- | ------------- |
| `id`          | BIGINT (PK) | 主键，自增 ID      |
| `name`        | VARCHAR     | Collection 名称 |
| `created_at`  | DATETIME    | 创建时间          |
| `description` | VARCHAR     | Collection 描述 |


**约束：**
* `PRIMARY KEY (id)`

---

### **2. documents**

| 字段              | 类型          | 说明            |
| --------------- | ----------- | ------------- |
| `id`            | BIGINT (PK) | 主键，自增 ID      |
| `collection_id` | BIGINT (FK) | 所属 Collection |
| `title`         | VARCHAR     | 论文题目          |
| `md_text`         | TEXT     | 论文转换后的markdown格式的全文        |
| `file_name`     | VARCHAR     | 文件名           |
| `file_path`     | VARCHAR     | 文件落盘路径          |
| `file_sha256`   | VARCHAR     | 文件内容的 SHA-256 哈希，用于去重 |
| `file_size_bytes` | BIGINT   | 文件字节大小        |
| `num_pages`     | INT         | 页数            |
| `element_count`     | INT         | 文档包含的元素总数     |
| `created_at`    | DATETIME    | 创建时间          |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (collection_id)` → `collections(id)` ON DELETE CASCADE
  
> `collection_id + file_name + file_sha256` 作为上传去重键，防止同一 PDF 被重复解析入库。

---

### **3. elements**

| 字段              | 类型                                     | 说明                                       |
| --------------- | -------------------------------------- | ---------------------------------------- |
| `id`            | BIGINT (PK)                            | 主键，自增 ID                                 |
| `doc_id`        | BIGINT (FK)                            | 所属文档                                     |
| `order`         | INT                                    | content_list中解析出的阅读顺序，从0开始                    |
| `elem_type`     | ENUM('text','header','image','table','equation') | 元素类型                                     |
| `header_name`  | VARCHAR                                | 章节标题，如1.1.1 message passing(不包括父标题)  
| `header_level`  | INT         | 章节标题层级，只有header类型的元素才有。                              |
| `level_nav`     | VARCHAR                 | 层级导航信息，如1. introduction > 1.1 GNN > 1.1.1 message passing      |
| `text_content`  | TEXT                                   | 文本内容                                     |
| `text_caption`  | TEXT                                   | 图片或表格caption注解                                |
| `image_base64`  | TEXT                                     | 图片内容（Base64 编码）                          |
| `bbox_json`     | JSON                                   | 元素在 PDF 中的位置信息, 4个int组成的列表（bounding box） |
| `page_no`       | INT                                    | 页码                                       |
| `vec_embedding` | VECTOR                                   | 向量嵌入（用于相似度检索，维度由环境变量 `VECTOR_DIM` 配置） |
| `order_start_index` | INT                                   | Header 元素对应章节在阅读顺序中的起始索引（基于 `order`） |
| `order_end_index` | INT                                   | Header 元素对应章节在阅读顺序中的结束索引（基于 `order`） |
|                 |                                        |                                          |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (doc_id)` → `documents(id)` ON DELETE CASCADE

> 向量维度通过环境变量 `VECTOR_DIM` 配置。

---

### **4. chats**

| 字段                | 类型          | 说明                   |
| ----------------- | ----------- | -------------------- |
| `id`              | BIGINT (PK) | 主键，自增 ID             |
| `collection_id`   | BIGINT (FK) | 所属 Collection        |
| `created_at`      | DATETIME    | 会话创建时间               |
| `title`           | VARCHAR     | 对话标题                 |
| `max_evidence_no` | BIGINT      | 当前chat中最大的evidence编号, 从1开始编号 |
| `max_turn_order` | BIGINT      | the numer of turns in the chat, start from 1 |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (collection_id)` → `collections(id)` ON DELETE CASCADE

---

### **5. turns**

| 字段                 | 类型          | 说明                      |
| ------------------ | ----------- | ----------------------- |
| `id`               | BIGINT (PK) | 主键，自增 ID                |
| `chat_id`          | BIGINT (FK) | 所属会话                    |
| `order`            | INT         | 当前turn在chat中的顺序         |
| `user_question`    | TEXT        | 用户问题                    |
| `llm_answer_text`  | MEDIUMTEXT  | LLM 的回答                 |
| `llm_thought_text` | MEDIUMTEXT  | LLM 的推理过程（思考链）          |
| `created_at`       | DATETIME    | 创建时间                    |
| `response_tokens`  | INT         | 记录当前轮token消耗            |
| `used_llm_model`   | VARCHAR     | LLM 模型标识（如 llama3:70b 或 qwen2.5vl:72b） |

**约束：**

* `PRIMARY KEY (id)`
* `FOREIGN KEY (chat_id)` → `chats(id)` ON DELETE CASCADE

## 七、桥表（Bridge Table）

用于记录每一轮对话（Turn）中引用到的 Evidence 元素。
在该设计中，**Evidence 不再是独立实体**，而是由 `(chat_id, evidence_no)` 标识，并记录其出现于哪个 `turn_id`。
Evidence 编号在同一 `chat` 内从 1 开始连续递增，跨 turn 不重置；通过 `turn_order` 可恢复上下文顺序。

---

### **Turn2Evidence（表）**（实际表名：`turn2evidence`）

| 字段            | 类型          | 说明                                                     |
| ------------- | ----------- | ------------------------------------------------------ |
| `chat_id`     | BIGINT (FK) | 所属会话 ID，对应 `chats(id)`                                 |
| `turn_id`     | BIGINT (FK) | 所属轮次 ID，对应 `turns(id)`                                 |
| `turn_order`  | INT         | 当前 turn 在 chat 内的顺序（冗余字段，用于快速恢复上下文）                    |
| `evidence_no` | INT         | 在同一 chat 内从 1 开始连续编号（标记 `[Evidence#1]`、`[Evidence#2]` 等） |
| `element_id`  | BIGINT (FK) | 关联的文档元素 ID，对应 `elements(id)`                           |
| `created_at`  | DATETIME    | 记录创建时间                                                 |

---

**约束：**

* `PRIMARY KEY (chat_id, evidence_no)`
  → 保证每个 chat 内的 evidence 编号唯一且连续。
* `FOREIGN KEY (chat_id)` → `chats(id)` ON DELETE CASCADE
* `FOREIGN KEY (turn_id)` → `turns(id)` ON DELETE CASCADE
* `FOREIGN KEY (element_id)` → `elements(id)` ON DELETE CASCADE

> 性能相关索引（例如 `(turn_id, element_id)` 等）将于端到端流程稳定后再评估与添加，避免过早承诺。


---

## 三、结构要点总结

* 所有表均为 **全局共享结构**，不同 `collection` 的数据通过collection_id外键区分。
* `elements` 表是核心索引层，支持多模态内容检索（文本 + 图像 + 表格）。回答阶段（DSPy）仅消费 `text_content`/`text_caption` 形成的文本上下文；若需要利用图像语义，则由后端集成读取 `image_base64` 调用视觉问答接口，将结果转为文字再回注为 `text_content` 使用。
* `turn2evidence`：动态绑定 Turn ↔ Evidence ↔ Element，实现证据记录和追踪。
* `evidence_no` 在每个 `chat` 内 **独立递增，从 1 开始**。
