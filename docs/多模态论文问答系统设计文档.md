
# 板块设计

| 模块                     | 当前你的设计                                                                          | 说明            |
| ---------------------- | ------------------------------------------------------------------------------- | ------------- |
| **Evidence 生成策略**      | Answer 生成时 LLM 输出 `[Evidence#]` 锚点，锚点对应已索引的 Element，含 bbox，可直接前端高亮              | 结构清晰，前后端可一一映射 |
| 索引元素                   | MinerU解析出的content_list中的每个对象就是一个Element，作为基本索引单元，既可以是文本，也可以是image，实现多模态统一索引和检索。 |               |
| **Answer–Evidence 绑定** | 在 Answer 文本内嵌 Markdown 锚点 `[Evidence#]`，前端点击跳转高亮                                | 标注机制明确        |
| **高亮系统**               | 基于 MinerU 坐标信息渲染前端高亮                                                            | 可复用 JSON 坐标结构 |
| **系统结构**               | 顶层控制Agent 、检索 Agent、记忆维护 Agent、回答 Agent 4板块协作(方便后续扩展)；OceanBase 作为索引存储层。        | 模块边界合理        |

# 详细设计-pipeline

## 后端

### p1 上传和索引文档
解析pdf元素，加载得到的content_list以及其中对应的images， 使用preprocess_header , 扫描整个列表，修复章节标题层级(根据1 1.1 2.1.2 的特征来判断是几级标题)，为每个Element加上章节字段section_name(最近的上一个元素的标题名称)和层级字段level_nav(按标题层级从高到低产生的标题导航)。
并且进行下面的预处理：
按层次结构聚合各个section的内容(从当前标题到下一个等级相同的标题的所有文本内容，按顺序拼接)，用一个简单的摘要库生成一个summary，放到header节点中。
pdf存入Documents表中，要带上Collection信息


为了丰富检索时的信息，统一检索格式，要求Element都具有text_content和image_content 2部分内容。
pure_text、header只有text_content， 而image, equation, table 既有text_content又有image_content ；其中
- pure_text的text_content 由其 section_name + level_nav + text_content组成
- header元素的text_content 由其section_name + level_nav + section_summary组成
- image的text_content由其 section_name + level_nav + image_caption 组成
- table的text_content由其 section_name + level_nav + table_caption 组成
- equation的text_content由其section_name + level_nav + equation_text (通常解析为latex格式) 组成
- image、 table、 equation的image_content 由其content_list中的base64编码的图片组成。


根据元素的类型进行统一的embedding，API调用阿里的多模态embedding模型，对文本类型的Element(Text, Table, Equation)按文本嵌入，对图片类型的Element (image)按图片嵌入，之后按顺序将这些Elements存入向量数据库的Elements表中，带上Collection信息。 (虽然Table, Equation也有image_content，但是嵌入的时候我们还是用text_content来生成他们的embedding)

### p2 简单问答
选择一个Collection，进行提问，根据用户question, 让阿里LLM将其改写成query，然后用query去Elements表中向量检索Elements，按header、pure_text、table、equation、image分别返回，然后按顺序做Evidence编号，存一个Evidence2Element的映射，然后AnswerAgent根据不同元素中包含的text_content及其对应的element编号组装成prompt (image_content 要单独放到图片侧的输入里)，去问阿里的VLM模型，生成答案的同时在答案文本中间给出evidence锚点。
锚点的格式可以是 `[Evidence#1]` , `[Evidence#2]` 这种形式，每个锚点对应的元素都会有一个唯一的doc_id，bbox和page_no，所以点击时能够直接高亮对应的内容。

(因为标准VLM api的输入是 text: list[str], images: list[base64])，在prompt构造时，text的list和images的list需要一一对应(在prompt中进行相关的说明，显示给出images列表中每个idx位置图片对应的evidence_id)。
