## M1 Execution Plan — Database Initialization & Repository Layer

**Reference Docs**
- `docs/en/Develop_Road_Map.md` (Milestone scope & DoD)
- `docs/en/Data_Model.md` (table definitions, FK cascade, types)
- `docs/en/backend_frontend_interactive_design.md` (unified response envelope and `/api` prefix)
- `dependency/oceanBaseDemo/ob_sqlAlchemy_demo.py` & `ob_vector_utils.py` (connection + vector column patterns)

1. **Author the OceanBase schema DDL (idempotent)**
   - File to add: `EviQAsys/backend/app/repositories/sql/schema.sql`.
   - Content: `CREATE TABLE IF NOT EXISTS` statements for `collections`, `documents`, `elements`, `chats`, `turns`, `turn2evidence`. Do not create performance indexes in M1; optional indexes (e.g., `idx_chat_turn`, `idx_turn_element`) are deferred.
   - Types per `Data_Model.md`: use `VARCHAR` + `CHECK` for `elements.elem_type` (no ENUM), all tables use `created_at DEFAULT CURRENT_TIMESTAMP` where applicable, and `FOREIGN KEY` constraints use `ON DELETE CASCADE`.
   - Parameterise vector column dimension via environment variable `VECTOR_DIM` (implementation detail handled by the Python initializer); keep the SQL portable by noting `VECTOR(<VECTOR_DIM>)` intent in comments.
   - Database selection/creation is handled by the Python initializer (not inside the SQL file).

2. **Provide a reusable DB connection helper and env settings**
   - Files to add: `EviQAsys/backend/app/repositories/db.py`, `EviQAsys/backend/app/env_setting.py`.
   - `env_setting.py`: centralises environment variables and defaults (e.g., `OB_HOST`, `OB_PORT`, `OB_USER`, `OB_PASSWORD`, `OB_DEFAULT_DATABASE`, `DATABASE_CONNECT_TIMEOUT`, `VECTOR_DIM`).
   - `db.py`: SQLAlchemy-based connection factory using `utf8mb4` charset; expose a contextmanager and an initializer that issues `CREATE DATABASE IF NOT EXISTS <db>; USE <db>;` and executes schema statements. Prefer driver autocommit for DDL; do not require users to run SQL manually.
   - Repositories reuse exported constants (e.g., `VECTOR_DIM`).

3. **Create a lightweight repository base utility**
   - File to add: `EviQAsys/backend/app/repositories/base.py`.
   - Content: shared helpers for building SQL statements (e.g., `dict_to_insert`), a thin `RepositoryResult` dataclass, and wrappers to map cursor rows to dictionaries; centralises error handling/logging so concrete repositories stay focused on SQL text.

4. **Implement table-specific repositories (non-ORM gateways)**
   - Files to add under `EviQAsys/backend/app/repositories/`: `collections_repo.py`, `documents_repo.py`, `elements_repo.py`, `chats_repo.py`, `turns_repo.py`, `turn2evidence_repo.py`.
   - Content per file: repository class with CRUD methods matching roadmap needs (`create_*`, `get_by_id`, `list_by_foreign_key`, `update`, `delete`). Each method composes pure SQL strings (no ORM), uses the base helpers, and enforces FK relationships (e.g., `documents_repo.list_by_collection(collection_id: int)`). Return dict rows with keys equal to DB column names.
   - Include TODO placeholders for future vector search logic in `elements_repo` (in line with M3) and ensure `turn2evidence` repository exposes bulk insert helper for anchor binding.

5. **Expose repositories via package init**
   - Update file: `EviQAsys/backend/app/repositories/__init__.py`.
   - Content: import and re-export repository classes plus constants so service layers can do `from ....repositories import CollectionsRepository`.

6. **Define API-facing schemas**
   - Files to add under `EviQAsys/backend/app/schemas/`: `collection.py`, `document.py`, `chat.py`.
   - Content: Pydantic models (`CollectionBase`, `CollectionCreate`, `CollectionRead`, etc.) reflecting DB columns and typed to align with docs. Provide `Config` to allow orm_mode-like behaviour for dict rows.
   - Update `EviQAsys/backend/app/schemas/__init__.py` to export these models.

7. **Wire repositories into FastAPI endpoints**
   - File to add: `EviQAsys/backend/app/api/routes/collections.py`.
   - Content: APIRouter mounted under `/api` with `GET /collections` only (returns empty list initially via repository). Responses follow the unified envelope: `{"code":"OK","data":...}`.
   - Update (or create) `EviQAsys/backend/app/api/__init__.py` to expose `api_router`, and update `EviQAsys/backend/app/main.py` to instantiate `FastAPI`, include router with `/api` prefix, and register a startup initializer that creates/uses the target database and applies idempotent DDL. If OceanBase is unavailable at startup, fail fast with a clear error.

### 8. **Add manual repository verification scripts (no pytest)**

* **Files to add under** `EviQAsys/backend/tests/repositories/`:
  e.g., `check_collections_repo.py`, `check_documents_repo.py`
* **Content:**

  * Each script must be a **standalone Python file** with a `main()` function entrypoint, e.g.:

    ```python
    if __name__ == "__main__":
        main()
    ```

  * Scripts directly connect to a **real OceanBase instance** using environment variables and execute repository methods to verify CRUD behavior. Developers are responsible for cleaning up inserted test data; migration never drops existing data.

  * **No `pytest`, no mock data.**
    Tests must rely on actual database tables initialized from `schema.sql`.

  * Each script prints meaningful log outputs (e.g., created IDs, fetched rows, constraint errors) for manual inspection.

  * AI tools are only permitted to perform **static syntax checks**, not runtime execution or result fabrication.

  Example run:

  ```bash
  python EviQAsys/backend/tests/repositories/check_collections_repo.py
  ```


### 9. **Manual verification checklist**

Document in `docs/dev_log/M1.md` once implementation is done:

1. Start FastAPI (`uvicorn EviQAsys.backend.app.main:app --app-dir EviQAsys/backend --reload`). The app startup should initialize the database and apply idempotent DDL automatically.
2. Execute manual test scripts under `backend/tests/repositories/` and confirm CRUD works without errors; clean up any inserted rows as needed.
3. Call `GET /api/collections` and confirm response envelope `{"code":"OK","data": []}`.
4. Record results and console logs in the milestone validation log, satisfying roadmap DoD.
